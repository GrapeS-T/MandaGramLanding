# База знаний и SDK

Правила обновления статей, сверки возможностей клиента и сопровождения SDK. Все пути к файлам сайта указаны относительно корня репозитория; пути клиента относятся к отдельному checkout MandaGram.

## Как обновлять документацию движка

Источник истины — **реализация клиента MandaGram**, а не рекламный текст сайта, старый пример или комментарий SDK. Для сверки используйте соответствующий checkout [MandaGram](https://github.com/GrapeS-T/MandaGram):

- `src/native/include/mandagram_plugin.h` — порядок полей `PluginApi`, C-структуры и callback-сигнатуры; `.hpp` и `.zig` — обёртки и bindings.
- `src/main/kotlin/com/mandagram/plugin/bridge/` — FFM-мост, фактическая реализация API, TDLib JSON и Compose interop.
- `plugin/loader/`, `plugin/storage/`, `plugin/watchdog/`, `plugin/xposed/` в том же дереве — загрузка/перезагрузка, хранилище, учёт ошибок и перехват методов.
- `docs/development.md` и `docs/architecture/` клиента — карта подсистем, сетевые ограничения, пути portable-данных, UI и медиа. Возможности пользовательского интерфейса подтверждайте вызовами из UI, не только наличием enum или метода.

База знаний разделяет реализованные возможности и ограничения. Нативные плагины выполняются внутри процесса, не в песочнице; Watchdog не гарантирует восстановление после зависания или native crash. Наличие Slot API не означает, что произвольный Compose-компонент можно вставить в любую область UI. ABI не имеет поля версии или размера структуры: SDK и клиент должны соответствовать друг другу.

При изменении статей:

1. Редактируйте отдельный файл в `src/data/articles/`. Сохраняйте существующие slug и HTML-якоря; новый slug добавьте в порядок категорий `src/data/kb.ts` и sitemap. Заголовки h2/h3 должны иметь уникальный id либо находиться непосредственно в section с уникальным id. Оглавление, число разделов, примерное время чтения (150 слов/мин), prev/next и названия в каталоге вычисляются, не дублируйте их вручную.
2. HTML в `content` — доверенный исходный текст, вставляемый через `set:html`, а не Markdown. Экранируйте `<`, `>` и `&` внутри примеров кода, обратные кавычки и `${...}` — внутри TypeScript template strings. Не вставляйте непроверенный пользовательский HTML.
3. Поисковый индекс строится из содержимого и заголовков разделов; отдельную копию `public/kb/search.json` не создавайте. Для API сохраняйте якорь с точным именем функции, чтобы поиск вёл непосредственно к контракту.
4. Порядок полей ABI и calling convention нельзя менять независимо от клиента. Публичный SDK привязан к commit движка и контрольным суммам; `public/examples/include/` — производная копия `public/include/`, не редактируйте её отдельно. Примеры используют тот же SDK; удаляйте устаревшие JNI bindings, не оставляйте параллельный несовместимый API.
5. Проверьте статью на локальном стенде: оглавление, переходы, переносы кода на узком экране, доступность ссылок на заголовки и примеры. Генерация индекса сама по себе не доказывает работу интерактивного поиска.
6. Не обещайте опубликованные пакеты, поддержку форматов, безопасность или UI-функции без подтверждения. Для risky-функций описывайте последствия: PIN не шифрует файлы, Panic удаляет локальные данные, сохранённый WEB-прокси блокирует сеть до явного изменения режима.

### Комплект SDK и проверки примеров

`npm run build` сначала проверяет контрольные суммы закреплённых headers, обновляет `public/examples/include/` и создаёт исходный архив `/sdk/mandagram-plugin-sdk.zip` с манифестом и инструкциями. Исходная ревизия и toolchain pins находятся в `scripts/plugin-sdk-source.json`; команды сборки — в `scripts/SDK-BUILDING.txt`. Архив детерминирован: LF, отсортированные пути, фиксированные даты, без бинарников, кешей и клиентских данных. Отдельная команда упаковки — `npm run sdk`; сверка с read-only checkout клиента — `npm run sdk:verify-source -- <путь-к-MandaGram>`.

При обновлении движка сначала сверяйте реализацию API и headers конкретного commit, затем обновляйте canonical `public/include/`, ревизию и SHA256 в source manifest, статьи и bindings Rust/D. Не обновляйте hashes только ради прохождения проверки: они обозначают проверенный источник ABI.

`.github/workflows/plugin-examples.yml` отдельно собирает C++, Rust, Zig и D, включая рецепты, на Windows/Linux x64 из распакованного архива. Экспорты проверяются через `npm run examples:exports -- <библиотеки>` (dumpbin/nm). Наличие workflow не означает успешного запуска. Сверка исходников, компиляция и загрузка в клиент — разные уровни проверки; source manifest не удостоверяет runtime-совместимость. Сборка сайта не запускает компиляторы плагинов и клиент.
