# Git: ветки, интеграция и коммиты

## Ветки и правила интеграции

- `main` — стабильная ветка. Изменения попадают в неё только через pull request из `dev`, после проверки и ревью. Прямые коммиты и прямой push изменений в `main` запрещены.
- `dev` — интеграционная ветка для следующего выпуска и dev-сборок. В ней не разрабатывают напрямую: изменения поступают merge из рабочих веток.
- `feat/<short-name>` — отдельная ветка для каждой новой фичи, создаётся от актуальной `dev`.
- `fix/<short-name>` — исправления, также от `dev`. Крупный самостоятельный фикс — отдельная ветка; исправления незавершённой фичи можно делать в её `feat/*`.
- Для документации, обслуживания и рефакторинга используй аналогичные рабочие ветки: `docs/*`, `chore/*`, `refactor/*`.
- Имена — короткие английские слова в kebab-case: `feat/chat-search`, `fix/profile-music`, `docs/git-workflow`.
- По умолчанию на remote поддерживаются долгоживущие ветки `dev`, `main`, `release` и другие явно согласованные постоянные ветки. Рабочие ветки (`feat/*`, `fix/*`, `docs/*`, `chore/*`, `refactor/*`, например `docs/engine-and-team`) остаются локальными: после проверки их вливают в `dev` через merge commit (`--no-ff`) и пушат `dev`.
- Публиковать рабочую ветку можно только по явному запросу разработчика на публикацию именно этой ветки. Общее поручение «сделай коммиты и запушь» не является таким разрешением: используй локальную рабочую ветку → merge в `dev` → push `dev`. Наличие upstream или ранее опубликованной рабочей ветки не отменяет это правило. Не используй `git push --all` или `--mirror`; указывай целевую ветку явно.
- Это правило не разрешает прямой push изменений в `main` и не означает публикацию сайта: `main` обновляется через PR из `dev`, а push в `release` выполняется только по отдельному поручению на деплой. Уже опубликованные рабочие ветки не удаляй без явного поручения.
- Отдельные `release/*` и `hotfix/*` пока не используются. Их процесс вводится по необходимости, а не предполагается агентом.

Последнее уточнение командного соглашения («в dev только мержи») заменяет первоначальное разрешение небольших прямых фиксов. Небольшой размер изменения не отменяет рабочую ветку.

## Порядок работы

1. Проверь текущую ветку и рабочее дерево. Не переключай ветки поверх чужих незавершённых изменений; не используй автоматические stash/reset/clean для освобождения дерева.
2. Получи актуальную `dev` и создай рабочую ветку. Разработка, коммиты и первичная проверка выполняются в ней.
3. Перед интеграцией обнови информацию об удалённой `dev`, включи её изменения в рабочую ветку, разреши конфликты и повтори затронутые проверки. Не откладывай проверку совместимости до PR в `main`.
4. Когда фича полностью реализована и проверена, влей её в `dev` через merge commit (`--no-ff`). Сохраняй границу фичи в истории; не заменяй merge копированием файлов, cherry-pick или squash.
5. Проверь интегрированное состояние `dev` на явные баги, вылеты и взаимодействие изменений. Локальная сборка и запуск описаны в [development.md](development.md#локальный-запуск); проверки статей и SDK — в [content.md](content.md). Для UI проверь реальные страницы на широком и узком экране, обе темы, клавиатурную навигацию и изменённые взаимодействия: одной сборки недостаточно.
6. Открой PR `dev` → `main`. В PR выполняются подробная проверка и ревью. Укажи изменения, проверки, известные ограничения; исправления замечаний проводи через рабочие ветки → `dev`, чтобы PR обновлялся тем же путём.
7. После устранения замечаний и успешной проверки PR мержится в `main`. Релиз собирается из принятого состояния `main`.

До завершения выпуска согласовывай новые merge в `dev`: открытый PR `dev` → `main` включает и последующие коммиты `dev`.

### Пример локальной интеграции фичи

Команды ниже предполагают чистое рабочее дерево, remote `origin` и существующую локальную `dev`. Выполняй шаги поэтапно, а не весь блок вслепую; при ошибке или конфликте остановись. Коммит, merge и push выполняются только в рамках порученной операции.

```bash
git status --short --branch
git fetch origin
git switch dev
git merge --ff-only origin/dev
git switch -c feat/chat-search

# Реализовать фичу, проверить её, добавить только относящиеся к ней файлы.
# Заголовок: feat(chat): add message search; body — все изменения этого коммита.

# Перед интеграцией получить изменения dev и проверить совместимость.
git fetch origin
git merge origin/dev
# Разрешить конфликты, завершить merge и повторить проверки при необходимости.

git switch dev
git merge --ff-only origin/dev
# В редакторе укажи заголовок type(scope): description и полный перечень изменений ветки в body.
git merge --no-ff feat/chat-search
# Проверить интегрированную dev перед публикацией.
git push origin dev
```

Если `--ff-only` или push отклонён, выясни расхождение истории; не используй force push. Получи новые изменения, согласуй интеграцию и повтори проверки. Не переписывай опубликованную историю `dev`/`main` и не обходи branch protection. Пример не выполняет merge в `main`: этот шаг допускается только через PR.

## Формат коммитов

Используй Conventional Commits для обычных и merge-коммитов. Заголовок — `type(scope): description`, как `fix(chat): isolate unavailable reply previews from conversation errors`:

```text
<type>(<scope>)[!]: <description>

<body: полный перечень изменений>

[footer]
```

- `type` обязателен: `feat` — новая возможность; `fix` — исправление; `refactor` — изменение структуры без смены поведения; `perf` — производительность; `docs` — документация; `test` — тесты; `build` — сборка, зависимости и упаковка; `ci` — CI; `chore` — обслуживание; `style` — только форматирование кода, не изменение UI.
- `scope` обязателен: затронутая подсистема, например `chat`, `network`, `media`, `i18n`, `windows`, `build`, `git`. Для сквозных изменений используй `app`; не перечисляй весь проект в заголовке.
- `description` — кратко на английском, в повелительной форме, без точки: `add`, `fix`, `preserve`, `remove`. Ориентир для заголовка — до 72 символов; ясность важнее механического сокращения.
- Один коммит — одно логически связное изменение. Не смешивай фичу с посторонним форматированием, обновлением зависимостей или чужими правками.
- Body обязателен: перечисли все изменения, включённые в коммит, отдельными пунктами — что добавлено, исправлено, изменено или удалено, включая код, тесты, документацию, сборку и конфигурацию. Описывай содержание изменений, а не только имена файлов; не ограничивайся главным изменением. При необходимости добавь причину решения и ограничения; указывай только реально выполненные проверки.
- `!` и footer `BREAKING CHANGE: ...` используй для несовместимого изменения публичного контракта или пользовательского формата; объясни миграцию. Обычный внутренний рефакторинг не требует этого маркера.
- При наличии задачи указывай её в footer (`Refs: #123`, `Closes: #123`) с реальным номером.

Примеры заголовков:

```text
feat(chat): add message search
fix(media): release profile player on account switch
refactor(network): consolidate file download state
docs(git): document branch and commit conventions
build(windows): update bundled VLC runtime
ci(build): build development tags
```

### Описание merge-коммитов

- Заголовок merge-коммита следует тому же формату `type(scope): description`, например `chore(git): merge chat search into dev`. Стандартный `Merge branch ...` или автоматически созданный заголовок merge PR нужно заменить на этот формат.
- Body обязателен и перечисляет все изменения, которые вливаемая ветка приносит в целевую ветку, по всем её коммитам, а не только последнему. Перед merge сверь историю ветки и итоговый diff относительно целевой ветки; не включай уже присутствующие в ней изменения.
- Укажи добавления, исправления, изменения и удаления, в том числе тесты, документацию, сборку и конфигурацию. Отдельно опиши изменения, внесённые при разрешении конфликтов. Ссылка на ветку/PR или фраза «merge branch» не заменяет полный перечень.
- Для merge PR подготовь заголовок и body итогового merge-коммита по тем же правилам; не полагайся на автоматическое описание хостинга.

## Теги и сборки

Локальная сборка сайта (`npm run build`) не является публикацией. Команды — в [development.md](development.md#локальный-запуск), публикация принятого `main` через fast-forward в `release` — в [deployment.md](deployment.md).

- Сайт публикуется по SHA коммита `release`; создание версии или тега не требуется для деплоя.
- Создание и публикация тегов — отдельное поручение. Если тег нужен, используй аннотированный тег на проверенном коммите и согласованное имя; публикуй только этот тег, не все локальные теги.
- Опубликованные теги не перемещай и не переименовывай. Коммит, тег и сборочный артефакт должны соответствовать друг другу; тег сам по себе не меняет версию в [package.json](../package.json).
- Правила версий, prerelease и Windows-пакетов клиента относятся к [репозиторию MandaGram](https://github.com/GrapeS-T/MandaGram), а не к статическому сайту.

### Что автоматизировано сейчас

- [deploy.yml](../.github/workflows/deploy.yml) собирает сайт на Node.js 22 и публикует production только из `release`; поддерживает push и ручной запуск. `dev` и `main` сайт не публикуют.
- [plugin-examples.yml](../.github/workflows/plugin-examples.yml) компилирует примеры SDK на Windows/Linux x64 при затрагивающих SDK pull request и push в `dev`, `main`, `release`, а также вручную. Это проверка компиляции и экспортов, не загрузка плагинов в клиент.
- Автоматического создания тегов или GitHub Releases в этих workflows нет.
